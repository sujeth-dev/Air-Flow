01 / REAL-WORLD PRODUCT

The problem it actually solves

Every explanation of a spatial or structural thing — a cell, a circuit, a mechanism, a floor plan — hits the same wall: the explainer understands it, the audience has to imagine it. Slides and whiteboards are static and prepared in advance, so they break the moment someone asks "what if it looked like this instead?" AirDraw closes that gap live, and does it touchlessly — which unlocks contexts a mouse or touchscreen can't.

Who it's for

  • Presenters & teachers at a board or on a stage who can't reach a keyboard mid-flow.
  • Hands-busy / hygiene-sensitive spaces — labs, workshops, clinical-adjacent demos, public kiosks and museum exhibits where no one wants to touch a shared screen.
  • Accessibility — an alternative input for users who can't use a precise mouse or stylus.
  • (Stage 2+) Technical sales / product demos — conjure and rotate a model in front of a prospect without breaking eye contact.

Why it's useful & easy

  • Zero install for the audience — it runs in a browser; only a webcam is needed.
  • Learnable in seconds — pinch to draw, release to snap. No drawing skill required: presets fix your messy stroke.
  • Explanation → shared visual instantly, instead of "picture this in your head."
  • Works where touch doesn't — across a room, on a stage, or on a screen no one should touch.

Core logic — gesture state machine

IDLE        no hand seen
  → hand detected ⇒ ARMED
ARMED       hand tracked, cursor shown
  → pinch (dist(thumb,index) < T_on) ⇒ DRAWING
DRAWING     append {x,y,t} each frame
  → release (dist > T_off) ⇒ RECOGNIZING
RECOGNIZING normalize → $1 → result
  → render & reset ⇒ ARMED

Use hysteresis (T_on < T_off) so the pinch doesn't flicker. Drop strokes under ~8 points.

Core logic — $1 pipeline

1. resample stroke → 64 even points
2. rotate so centroid→p[0]
   angle = 0 (indicative angle)
3. scale to 250×250 ref box
4. translate centroid → origin
5. for each template:
     avg point distance
6. score = 1 − dist / (0.5·√(2·250²))
7. best score > 0.80 ⇒ accept
   else ⇒ "not recognized"

Client state shape

{ trackingStatus: 'searching' | 'tracking' | 'lost',
  fps: number,
  fsmState: 'idle'|'armed'|'drawing'|'recognizing',
  currentStroke: {x,y,t}[],
  lastResult: { shape: string, score: number } | null,
  history: { shape, score, at }[] }

UI & design spec (keep quality high)

  • Layout: full-bleed dark stage; mirrored, dimmed webcam underlay; glowing fingertip cursor; fading trail; right-side history rail; bottom-left HUD.
  • States are visible: the FSM state drives the cursor color (armed = muted, drawing = acid glow, recognizing = pulse). Users should always know if the "pen is down."
  • Forgiving feedback: on "not recognized," show the closest guess + a hint, never a dead end.
  • Onboarding: first-run overlay — "Allow camera → pinch to draw." Handle denied-permission and poor-lighting explicitly.
  • Accessibility: respect prefers-reduced-motion; keyboard fallback to pick shapes; AA contrast; captioned status text (not color-only).
  • Presenter mode (ships in S1): a HUD toggle that goes true-fullscreen and hides the history rail + controls, leaving only the canvas — ready for browser tab-share into Zoom/Meet (see §06).
  • Tokens: reuse the shared design system in §05 so Stage 1 and 2 look like one product. Thicken strokes & max contrast in presenter mode so shapes survive video compression.

ML plan (the resume centerpiece)

  • Data: Google QuickDraw .npy bitmaps — ~12 classes matching your presets (circle, square, triangle, star, arrow, line + a few organic ones), a few thousand samples each.
  • Preprocess: 28×28 grayscale, normalized 0–1 (QuickDraw native size).
  • Model: small CNN — [Conv→Conv→Pool]×2 → Dense → softmax; aim <2 MB after quantization.
  • Train: Keras in Colab; target ≥92% held-out accuracy; export to TF.js with tensorflowjs_converter.
  • Inference: rasterize the air-drawn stroke onto an offscreen 28×28 canvas → tf.browser.fromPixels → predict → argmax. Target <50 ms.
  • Hybrid logic: if $1 score is high & shape is geometric, take it (fast); else defer to the CNN. Log which path fired (measurable "ML beats baseline" story).

05 / SHARED DESIGN SYSTEM

One look across both stages

Define these tokens once (tokens.css) and consume everywhere so Stage 1 and Stage 2 read as a single, intentional product — not two demos.

Tokens

--acid #c8f24e--cyan #5fd4d6--bg #0c0d10--panel #131519--ink #e9ece8

Type: Bricolage Grotesque (display) · Hanken Grotesk (body) · JetBrains Mono (labels/data). Radius 14px. 8px spacing grid.

Principles

  • Dark, instrument-panel calm so the glowing trail/object is the hero.
  • Acid = "live / your action"; cyan = "system / data"; warn = "attention."
  • Motion only where it informs: the morph, the recognizing pulse, staggered loads. Honor reduced-motion.
  • Every interface state has an explicit visual — never leave the user guessing if the pen is down.

Phase 1 · Zero-friction tab sharing — Zoom / Meet

  • Stage 1 is client-side, so the simplest broadcast is the browser's own screen-share. No code beyond UI.
  • Presenter Mode toggle (built in S1): true fullscreen via the Fullscreen API, hide history rail + controls + chrome, canvas only.
  • Compression-safe tokens: in presenter mode, thicken canvas strokes and push --acid-on---bg contrast so shapes don't smear into artifacts on low-bandwidth video.

Phase 2 · Native in-app recording — async demos & training clips

  • Tech: canvas.captureStream(30) → MediaRecorder, fully client-side, no external recorder.
  • Codec: default to video/webm;codecs=vp9 (vp8 fallback). mp4 from MediaRecorder is not reliably supported across browsers — record webm, offer optional transcode later.
  • HUD "Record" module: buffer chunks in memory, then drop a download link (airdraw-session.webm) on stop.
  • 3D note: for the Three.js canvas, init the renderer with preserveDrawingBuffer: true so captured frames aren't blank.

Phase 3 · Studio overlay — transparent virtual camera

  • Tech: in-app chroma-key toggle + OBS Studio Virtual Camera (desktop app — a documented user workflow, not something the app automates).
  • In-app part: a toggle that swaps --bg to pure #00FF00.
  • User workflow: OBS → Window Capture of the browser → Chroma Key filter (green) → layer webcam/slides beneath → Start Virtual Camera → select "OBS Virtual Camera" in Zoom/Meet. The drawings float, transparent, over the presenter.
Reality check: Phases 1–2 are app code an agent can build. Phase 3 depends on OBS, a desktop program the agent can't install or configure for you — the app only ships the green-screen toggle; the OBS steps are for you to follow.
07 / EXECUTION

How to run this plan

  • By hand: work top-down M0→M6 within a stage; don't start a milestone until the previous done-criterion is observably true.
  • With a coding agent (e.g. Claude Code): each milestone is self-contained — hand over the stack, file tree, and done-criterion for one milestone at a time, review against the criterion, then proceed. The schema and API specs above are copy-paste ready.
  • Always shippable: deploy at M0 and keep it green; you'll always have a live link to show.
What an agent can one-shot vs. not: Stage 1 (incl. streaming Phase 1–2) is fully autonomous — it's pure client-side code. Stage 2 needs you to create a Supabase project + paste keys and to train/convert the CNN (a Colab step); the agent scaffolds everything else. Stage 3 needs a deployed socket server, and streaming Phase 3 needs desktop OBS. So "build it all in one prompt" realistically means all of Stage 1; later stages are agent-built around a few manual prerequisites.
